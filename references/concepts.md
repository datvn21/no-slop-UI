# Concepts for an open brief

Use when the user gives a category or goal but little visual direction, such as “make a site for my studio” or “make this dashboard feel less generic.” Do not use this to invent missing product facts. If even the product or primary job is unknown, ask for that one missing piece before committing to a build. If the user requests several concepts, present genuinely different directions; otherwise compare internally and build the strongest one.

For a substantial concept, use [current UI research](inspiration.md) to inspect relevant products before committing to a structure. Borrow a decision about hierarchy or interaction only when it fits the user's task and material. Keep the product's own brand and content.

## Make candidates from the product, not style names

Start with the known **object** (what users view or change), **action** (what they came to do), **material** (real content and assets), and **setting** (device and use context). Generate two or three candidates by changing the organizing idea, not only the palette. These lenses are prompts, not presets:

| Lens | Ask | Example when evidence supports it |
| --- | --- | --- |
| Object | Can the real product item occupy the first view? | A bookshop leads with its current catalog, not a generic brand promise. |
| Action | Can users try the main task immediately? | A calculator opens with the input and result, not feature cards. |
| Sequence | Does the task have a meaningful before, during, and after? | A repair service shows the actual intake and status path. |
| Evidence | Is there a real artifact that proves the offer? | A studio opens with work and project notes, not invented client logos. |
| Place or material | Is the physical context part of the product? | A venue uses its own signage, room, and program if supplied. |
| Comparison | Do users choose among options or states? | A plan page aligns meaningful differences in one view. |

For each candidate, write only four lines: **main subject; reading order; primary action; why this structure belongs to the available material.** Reject candidates that need invented content, hide the task, or merely rename a familiar hero/cards/CTA layout. A concept should change what the user sees or does, not just the adjective used to describe the look.

## Decide when to ask and when to infer

- **Ask once** when missing information changes the core job, factual claim, action destination, required platform, or mandatory brand constraint. Bundle related critical questions. Do independent work while waiting.
- **Infer and state the assumption** for reversible choices such as spacing density, a provisional palette, or which of two viable compositions to build. Preserve any existing design system.
- **Keep unknowns visible** in a concept. A product name, real price, logo, testimonial, photo, or booking endpoint cannot be inferred from a category.
- If the user asks for “three ideas,” present distinct concepts with a short fit and cost for each; recommend one. If they ask to “build it,” select one and proceed unless a critical fact blocks the build.

## Choose the direction

Compare candidates on task clarity, fit to real material, distinction from the category default, platform fit, and implementation cost. Pick the simplest candidate that makes the product's actual subject memorable. Explain the chosen direction in a few sentences. Do not ask the user to approve an abstract mood when the requested work can already be built and reviewed.

Example with a vague brief, “Make a page for a local cinema”: the product category is known, but the films, showtimes, booking route, and brand are not. The next useful work is to ask for the program and booking method, or make a clearly labeled prototype if that is what the user requested. “Dark cinematic with glowing cards” is only category styling; it is not a concept for this cinema.
